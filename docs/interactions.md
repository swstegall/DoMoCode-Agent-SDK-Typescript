# Interactions

DoMoCode exposes human-in-the-loop work as typed, correlated interaction requests. A
permission request has `kind: "permission"`; a question has `kind: "question"`; future
`*_request` frames are surfaced as an open-kind interaction with its raw payload. The
registry key is `(sessionId, id)`, so an id reused by a server run replaces the old ask and
aborts its signal.

## Session API

```ts
const session = await client.sessions.create();

const stop = session.onInteraction(async (ask) => {
  if (ask.kind !== "permission") return "decline";
  await ask.allow();
});

for await (const ask of session.interactions()) {
  if (ask.kind === "question") await ask.answer([{ selectedLabels: ["Yes"] }]);
}
```

`session.interactionRuntimeFor(options)` returns the underlying `InteractionRuntime` when
an application needs both its iterator and handler registration. `session.onInteraction()`
and `session.interactions()` share one dispatcher; they do not open competing event streams.
Each ask exposes an `AbortSignal`. It aborts when the server broadcasts the corresponding
resolved event, including when another attached client wins a race. Answer methods are
idempotent at the protocol boundary: stale or duplicate answers receive a successful
response from the server, while an observer still receives a typed authority error.

Handlers run newest-first. Returning `"decline"`, or calling `ask.decline()`, passes the ask
to the next handler. If no handler claims it, the configured policy tier runs. An iterator
that is already waiting claims the ask before handlers and policy, which pauses policy
fallback. Unhandled asks produce a warning through `console.warn` by default and receive a
second warning after `idleMs`; applications can replace the warning sink.

## Permissions and questions

```ts
const policy = permissionPolicy({
  rules: [
    { pattern: "src/generated/**", action: "allow" },
    { pattern: "src/**", action: "deny" }
  ],
  default: "ask",
  timeout: { after: 10_000, action: "deny" }
});

const runtime = session.interactionRuntimeFor({ policy });
```

Rules use last-match-wins glob semantics. `ask.allow({ always: true })` writes a persistent
server-side grant and therefore requires `allowPersistentGrants: true`; it is also rejected
when the server sets `disableAlways`. `yolo()` answers permissions once and selects every
question option. The policy question fallback cancels an unanswered question after its
configured timeout.

The low-level methods remain available for integrations that do not use the dispatcher:
`session.answerPermission(requestId, "once" | "always" | "reject", message?)` and
`session.answerQuestion(requestId, answers | null)`, where `null` cancels a question.

## Authority and lifecycle

Only the current session authority may answer. Attach with `authority: "require"` for
scripts that must drive a run, or `authority: "prefer"`/`"observer"` for read-only clients.
`session.dispose()` releases authority, flushes the event cursor, detaches the client, and
stops the stream; it never aborts the server run. An abort or force-clear on the server
drains pending asks with resolved events, so their signals terminate and no answer should
be attempted afterward.

Permission asks generated by child sessions are currently re-parented by the Swift server
onto the parent stream. Questions remain on the child stream on older servers, so a
subagent-aware application must attach a child observer until the server-side routing is
unified. The SDK's subagent interaction coordinator is added in the subagent phase.
